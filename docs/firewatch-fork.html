Your Own FireWatch

Take a copy of the repository, point it at a different municipality, and let GitHub poll the satellites, host the map and send the SMS — on free infrastructure, with no server of your own.

This is the deployment with no machine in it. GitHub Actions runs the poller, the repository itself stores the database, and GitHub Pages serves the map and these pages. Nothing about the pipeline is specific to Bosnia — but one thing about your location decides whether this is worth doing at all, so start there.

01 Will it work where you are

FireWatch is near-live because of one feed: Meteosat MTG, which is geostationary over 0° longitude and publishes a new fire field every ten minutes. Beyond roughly ±60° of longitude it cannot see the ground at all. The other two feeds are global, but they are polar-orbiting and about three hours behind.

So before anything else, find your longitude. These counts are detections returned for a 36-hour window over deliberately-burning test boxes, so a zero means the satellite is blind there rather than the sky being quiet:

Off the disc it still works — just not fast

Outside roughly 60°W–60°E you keep VIIRS, MODIS and Sentinel-3, so you keep global coverage, the clustering, the map, the history and the SMS. What you lose is the ten-minute feed, and with it the point of the whole exercise: alerts arrive about three hours after the satellite saw the fire instead of forty minutes. Decide whether that is still useful to you before spending an hour on setup.

Meteosat answers an out-of-disc query with HTTP 200 and an empty feature list, never an error — identical to a quiet sky. That is why the table above uses boxes that were definitely burning.

02 What you are switching on

Three GitHub features doing three jobs, and no server anywhere:

PieceJobWhere it lives
Actions — poll.yml On each external trigger: fetch the three feeds, cluster, diff, send SMS, render the map and the documentation .github/workflows
The repository Stores the SQLite database between runs, committed back by the workflow when the detection count moves state/firewatch.db
Pages Serves the map at / — the link that goes out in every alert — and this documentation at /docs/ public/

The runner is stateless, which is why the database is committed back into the repo: that commit is the memory. It carries the detections already seen and the record of which alerts already went out, so the next run does not re-text you about the same fire.

The cost of free

Money: nothing. Actions minutes are unlimited on public repositories and Pages is free with them. Keep the repository public — a private one bills Actions minutes and needs a paid plan for Pages.

Latency: the workflow is triggered from outside rather than by GitHub's own scheduler, so the cadence is yours to pick — see §08. Meteosat is already ~25 minutes behind the flame front and a runner takes a moment to start, so a 10–15 minute cadence puts an alert 30–45 minutes behind it, against the 25–35 an always-on host gives you.

03 Take a copy

Two routes, and the quieter one is not the fork button.

A clean copy recommended

The upstream repository accumulates a commit every time the detection count changes — that is the design — so its history is mostly Bosnian database blobs you have no use for. Starting fresh gives you a repository whose history is your own:

git clone --depth 1 https://github.com/mirza-basic/firewatch.git my-firewatch
cd my-firewatch
rm -rf .git
git init -b main

# create an EMPTY public repo on GitHub first, then:
git remote add origin https://github.com/<you>/<repo>.git

Or fork it

A fork keeps the link upstream, so you can pull improvements later. The trade is that you inherit the whole history, and that a fork starts with its workflows switched off. You have to enable them by hand on the Actions tab before anything runs, and until you do, every trigger you send is rejected.

Either way, do not push yet. The next three sections change files that you want in your first commit.

04 Three GitHub settings

All three are silent when wrong. The workflow will run, go green, and publish nothing.

  1. Let Actions write to the repository

    Settings›Actions ›General› Workflow permissions› Read and write permissions

    The workflow commits the database back after every cycle. Without write access the poll succeeds, the push fails, and the run ends red — and worse than red: the detections and the record of what was already alerted die with the workspace, so the next run re-discovers the same fire and texts about it again.

  2. Publish Pages from Actions, not from a branch

    Settings›Pages ›Build and deployment ›Source› GitHub Actions

    The map is uploaded as a deployment artifact, never committed to a branch. Left on the default "Deploy from a branch", the deploy step fails and the map never appears.

  3. Enable Actions if you forked

    Actions tab› I understand my workflows, go ahead and enable them

    Skip this on a clean copy — workflows in a repository you created yourself are already live.

05 Point it at your municipality

One command. It fetches the boundary and the settlement list, writes data/place.json, and that file is the only thing in the repository that names a place — the map title, the notification wording, the reference point every distance is measured from and the SMS all read it. No module needs editing.

Do this on your own machine, in your clone. You need Python with requests:

python3 -m pip install requests certifi

python3 -m firewatch setup "Općina Kakanj"

Search the administrative name, not the town. "Kakanj" is a place node with a Point geometry and no area to clip against; "Općina Kakanj" is the boundary relation you actually want. If several relations match, all of them are printed and --index N picks one.

  Looking up 'Općina Kakanj' ...
  Općina Kakanj, Zeničko-dobojski kanton, Federacija Bosne i Hercegovine, ...
  relation 2528213 · centre 44.175492, 18.142017 · id kakanj
  Fetching settlements within 25 km ...
  https://overpass-api.de/api/interpreter: 506 places
  wrote kakanj.geojson (601 vertices)
  wrote kakanj-settlements.json (506 places)
  wrote place.json

Useful flags: --lang bs sets the language the map opens in (it ships with English and Bosnian), --radius 25 the settlement search radius in km, --id the short name used for filenames, --force to overwrite an existing profile.

Two ways this fails that look exactly like success

A regional Overpass mirror answers 200 and returns nothing. overpass.osm.ch is a Switzerland-only extract: it answers HTTP 200 with {"elements": []} for anywhere else, indistinguishable from "no settlements here". An empty list would label every fire with bare coordinates, so setup treats it as a failed request and tries the next mirror — and if none answer, writes nothing and tells you to run it again. That is not a bug to work around; run it again.

A half-written place. Overpass fails often enough that this matters: everything is fetched before anything is written. A run that dies at the settlement step leaves your repository exactly as it was, rather than holding one place's outline and another's profile.

  1. Rebuild the map band

    python3 -m pip install shapely pyproj
python3 -m firewatch buffer

    This draws the dashed 2 km "nearby" band around the outline. It is the only command in the project that needs shapely and pyproj, and they are imported inside that one function, so the workflow still installs only requests and certifi. Skip this and the map simply draws no band — the page omits it rather than drawing a confident line in the wrong place.

  2. Set the timezone, and the name forms if you are not in English

    setup writes "timezone": "UTC", because it cannot know yours, and the map stamps every time in it. Set it to a real zone.

    The name forms it cannot generate either, and it says so rather than guessing. English is written correctly; any other language is seeded with the English wording and needs four strings, once:

    "names": {
  "bs": {
    "title":   "FireWatch Kakanj",      // tab and header
    "area":    "Općina Kakanj",         // as a heading says it
    "of":      "od Kaknja",             // after a distance: "6 km SI od Kaknja"
    "in":      "u općini Kakanj",       // locative
    "outside": "izvan općine"           // a detection over the border
  }
}

    Wrong-but-obvious beats wrong-but-plausible: a generated genitive reads as broken Bosnian to the only people who will read it. Four lines is cheaper than a rule that is right most of the time.

  3. Check it

    python3 -m firewatch place

    Prints the live profile, where it was loaded from, the bounding box, the vertex and settlement counts, whether the band matches the configured buffer distance, and how much stored history falls outside the new clip. The poll workflow runs this every cycle, for one reason: a fork that never ran setup is still watching Zavidovići, and the symptom — an empty map, no alerts — reads as a broken feed or a missing key.

This has been run end to end

setup "Opcina Kakanj" against a neighbouring municipality produced a 601-vertex boundary, 506 settlements, a correctly built 2 km band, and a full poll cycle — all three feeds queried against the new bounding box, and a rendered map titled FireWatch Kakanj saying "Ništa nije detektovano u općini Kakanj niti u krugu od 2 km u ovom periodu."

06 Clear the Bosnian state

The repository ships with a live database in it. Those detections are clipped to the Zavidovići boundary and are meaningless to you — and if you leave them, your first map is a map of someone else's fires.

rm state/firewatch.db state/.detections

If you would rather keep the history than delete it — the two municipalities may overlap, and the feeds will not serve 400 days again — python3 -m firewatch reclip shows exactly which detections the new clip rejects and where they are, and --apply removes them after copying the database. Either way python3 -m firewatch place is the check: it reports how much stored history falls outside the configured clip, and the poll workflow prints it every cycle.

What each file does, so you know what you are deleting
FileHoldsIf you leave it
state/firewatch.dbDetections, events, and which alerts were already sent Bosnian fires on your map, forever
state/.detectionsLast committed detection count — the test for "did anything change" Your first real detections look like no change, so nothing commits
state/config/config.json{"auto_expose": false} — keep it Nothing. It is not location-specific

Give yourself history on day one

A fresh database makes the 7-day and 30-day views misleading rather than useful, and nothing backfills on its own. Fill it locally before the first push, then commit the result — the workflow inherits it:

export FIREWATCH_DATA_DIR=$PWD/state
export FIREWATCH_CONFIG_DIR=$PWD/state/config
export FIRMS_MAP_KEY=<your key>

python3 -m firewatch backfill 30      # ~5 minutes
git add state/firewatch.db

That is 30 days, stitched from six FIRMS windows (the API caps a query at 5 days) and 48-hour WFS chunks (a 30-day Meteosat query never returns). Backfilled fires that are already out raise no alerts — a new alert means newly burning, not newly discovered — so this will not text anybody.

07 Secrets

SecretWhere it comes fromWithout it
FIRMS_MAP_KEY firms.modaps.eosdis.nasa.gov — free, arrives in seconds VIIRS and MODIS are skipped and reported as [----], not as a failure. Meteosat and Sentinel-3 carry the cycle
HTTPSMS_API_KEY httpsms.com settings — your own Android phone is the gateway No SMS. Everything else runs
HTTPSMS_FROM The gateway phone's own number, E.164 (+387…) No SMS
FIREWATCH_SMS_TO Recipients, comma-separated, E.164 No SMS
Why recipients are a secret and not config

Normally the recipient list lives in config.json so it can be edited while the service runs. On a public repository that would publish your friends' phone numbers, so FIREWATCH_SMS_TO exists to override the file entirely. The trade is one-way: with it set the list is fixed for the life of the process, and sms-add / sms-remove refuse to run rather than write to a file nothing reads. To change who gets texted, edit the secret.

The workflow logs the recipient count, never the numbers — GitHub masks an exact secret value, not the individual numbers inside a comma-separated one, and that log is public.

08 The map URL

Nothing to do. Both workflows derive it from the repository they are running in — https://<owner>.github.io/<repo>, lowercased, and the bare domain if your repository is named <owner>.github.io. The step prints what it resolved, so you can read it off the first run's log.

Why this is derived and not written down

It used to be a literal in both workflow files, and it was the fork mistake that cannot be seen. The map link is resolved at send time; on a host there is no ngrok agent, so FIREWATCH_PUBLIC_URL is the only source. Left pointing at the repository you copied from it is still a valid, working URL. Nothing errors, no run turns red, and every SMS you send quietly links to someone else's fires.

Set the repository variable FIREWATCH_PUBLIC_URL (Settings → Secrets and variables → Actions → Variables, not Secrets) only if you serve the map somewhere else — a custom domain, or your own host. A variable set there wins over the derived value in both workflows.

The URL is part of the message, and the message is 160 characters

An alert is four lines and one segment, and the map link is one of those lines — every character of https://owner.github.io/repository is spent before a word of the fire is. With this repository's own URL the longest alert it can produce lands at 158 characters, two short of a second segment. A longer owner or repository name spends that headroom: measured against https://some-longer-org-name.github.io/firewatch-kakanj-monitoring the same alert reaches 170 and costs two segments, every time, for the life of the deployment.

You do not have to discover this from a phone bill. Both python3 -m firewatch sms-status and the test-sms workflow print the worst alert this place can produce — longest settlement name, absurd values, your URL — with its character count and the headroom left:

  worst alert  : 158 chars, 2 to spare - fits  (lang bs, reignited, "Ekološko izletište „Ontario”")

If it says otherwise, a shorter repository name is the cheapest fix.

Then decide what triggers it

poll.yml has no schedule: block. Its only trigger is workflow_dispatch, which means something outside GitHub has to ask it to run — a free cron service, a home server, anything that can make an HTTP request on a timer.

GitHub's own scheduler is the obvious alternative and the reason it is not used: cron there has a five-minute floor and is routinely delayed 5–30 minutes under load, which is a lot of drift to add to a feed that is already 25 minutes behind the fire. An external caller fires when it says it will.

POST https://api.github.com/repos/<you>/<repo>/actions/workflows/poll.yml/dispatches
Authorization: Bearer <token>
Accept: application/vnd.github+json
Content-Type: application/json

{"ref":"main"}
Three things that make this call fail

ref is required. Post an empty body and you get 422 Unprocessable Entity, not a message explaining what is missing.

The token needs Actions: read and write — a fine-grained personal access token scoped to this one repository is enough, and expires on a date you choose. Put a reminder somewhere: an expired token fails silently from GitHub's side, because nothing on GitHub knows it was supposed to be called.

Success is 204 No Content with an empty body. Do not treat "no response" as a failure and retry into a queue of duplicate runs.

Cadence is now yours to choose. Under ten minutes buys nothing — MTG publishes a new slice every ten minutes with ~25 minutes of latency, so polling faster only burns runs. Ten to fifteen minutes is the sweet spot.

10 Living with it

Nothing on GitHub will tell you it stopped

Because the trigger lives outside GitHub, GitHub has no opinion about whether it is still firing. If your cron service dies, its free tier lapses, or the access token expires, the workflow simply stops being called — no failed run, no red cross, no email. The map freezes at its last good render and keeps serving happily.

So monitor the caller, not the repository. The cheapest check is the map itself: its panel header carries the time of the last cycle, and a timestamp hours old on a page that loads fine is the whole failure mode in one glance.

One thing you no longer have to worry about

GitHub disables scheduled workflows on a public repository after 60 days without commits — a rule that has turned off many a quiet side project. It does not apply here: there is no schedule to disable. A workflow_dispatch trigger keeps working however long the repository sits still.

Why it does not commit every run

At a 15-minute cadence, committing every cycle would be 2,880 commits a month, each storing a fresh copy of the database — hundreds of megabytes carrying no new information. The database's bytes change every cycle by design, so the workflow tests the detection count instead and stages the database only when that moves.

FIRMS quota

The key allows 5000 transactions per rolling 10-minute window. A sweep of the four NRT datasets costs 8, so even at a 10-minute cadence that is 48 an hour — about 1% of one window's allowance. A 30-day backfill costs 48. You are not going to run out.

When it goes quiet

SymptomCause and fix
Nothing detected, ever, and you are outside Europe or Africa You are off the Meteosat disc — §01
Fires labelled by coordinates, no place names settlements.json is empty, almost certainly a regional Overpass mirror. Refetch from a global one
The band vanished from the map nearby_buffer_km changed without a rebuild. python3 -m firewatch buffer, commit the artifact
Long ranges are empty Nothing backfills on its own — §06
40–90 day old history is missing Not a bug. FIRMS near-real-time reaches back ~40 days and the archive lags ~3 months, so that window has neither until the archive catches up
The same fire texts you twice A failed push lost the run's state. Check write permissions — §04
FIRMS fails with Network is unreachable Already handled: FIREWATCH_FORCE_IPV4 is set in both workflows, because the runners have no IPv6 route and FIRMS is the one host that publishes an AAAA record. Do not remove it

Every source failure is isolated and logged with its reason, and one failing feed never blocks the others. A run that reports one dead source and still publishes a map is working as designed.

11 What stays Bosnian

Less than it used to be. setup and data/place.json take care of the place names, the reference point, the timezone and the language the map opens in, in every module at once. What is left is the language, which is a different question from the place:

WhatWhereMatters if
The map's second language — a full Bosnian translation including Slavic plural rules and the -a → -e genitive applied to settlement names. Replace the bs block, or delete it and keep English only mapgen.py → I18N you are not in the region
SMS wording. sms_language follows place.json, and both Bosnian and English wordings are written out in full — a third language means a third block sms.py → SMS_TEXT you want alerts in a third language
Compass bearings are computed in English letters and translated for display (NE → SI) mapgen.py, sms.py the same
The documentation you are reading, and everything in docs/, describes Zavidovići by name docs/ you publish the docs with your map — the build script does, by default
If you add a third language

Alert text is transliterated to ASCII before sending, because one non-GSM character switches the whole SMS to UCS-2 and drops the segment from 160 characters to 70. Add your block to SMS_TEXT, then run python3 -m firewatch sms-status: it builds the longest alert your place can produce — longest settlement name, absurd values, your map URL — and prints the headroom. The Bosnian and English wordings both fit in one segment here with two characters to spare, which is not much to lend.

FireWatch is near-live wildfire monitoring built for Grad Zavidovići, Bosnia. The pipeline is not specific to it: three satellite feeds, a municipality polygon, and clustering that turns scattered thermal anomalies into one tracked fire.

Detections are satellite thermal anomalies, not confirmed wildfires. Industrial heat, flares and agricultural burning all register, and cloud cover blocks detection entirely on every one of these sensors. Treat it as a screening signal and verify before acting.
