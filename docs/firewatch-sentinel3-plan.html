Sentinel-3 Fast Path

A plan for cutting Sentinel-3 fire detection latency from three or four hours to about ninety minutes, by taking the product from the EUMETSAT Data Store instead of the EUMETView map service. Written to be executed later, or not at all.

3–4 h
Latency after
~1.5 h
Extra passes
none
New dependencies
netCDF + numpy
Status: documented, deliberately not implemented

Nothing in this plan has been written. It exists because the measurements behind it were expensive to gather and would otherwise be lost. The recommendation is not to build this yet — see 07 for the conditions that would change that answer. Everything here was measured against the live services on 1 September 2026.

01 What it buys, and what it does not

Sentinel-3 detections currently reach FireWatch three to four hours after the satellite passes. The same product is finished and available roughly ninety minutes after acquisition. That gap — about two hours — is the entire prize, and it is worth being precise about how narrow that is.

It adds no passes. Sentinel-3A and 3B cross Zavidovići about 2.4 times a day between them, and no change to how the data is fetched affects when a satellite is overhead. Sentinel-3C launches on 14–15 September 2026, but it replaces 3A rather than joining it, and needs months of commissioning first.

It adds no sensitivity. The same instrument produces the same fire pixels. A fire below SLSTR's threshold stays invisible, and the gap that actually hurts this system — MTG needing roughly 9 MW before it registers anything — is untouched.

The one real argument for doing it

At ~1.5 h, Sentinel-3 would become the second-fastest feed, overtaking FIRMS at a measured median of 191 minutes. For a fire in the 3–10 MW band — too small for MTG, well within reach of SLSTR's 1 km pixels — that is a genuine two-hour head start on the only other feed that can see it.

A correction worth recording

Comparing first_seen against acquisition time in the database suggests Sentinel-3 latency of 7.5 to 13 hours. That figure is wrong. poller.py fetches 30 h of Sentinel-3 history every 20 minutes, so the fetch window cannot be the cause — those gaps are the poller not running overnight. Measure publishing latency at the service, never from first_seen.

03 Where the two hours go

FireWatch takes Sentinel-3 from view.eumetsat.int/geoserver/wfs, the same EUMETView gateway that serves MTG. That service is built for map visualisation: it ingests the product on its own schedule and republishes it as queryable points. The ingest is where the two hours are spent.

The Data Store is the product's source of record. It publishes the granule as soon as processing finishes, which the identifiers show is 50 to 143 minutes after the satellite looked.

Note the shape of the trade: the WFS does the spatial filtering server-side and hands back exactly the points inside the boundary. The Data Store hands over a three-minute frame spanning a 1400 km swath, of which Zavidovići is a rounding error. Two hours of freshness is bought with a download, a decompression, a scientific-array parse and a spatial filter that all now happen locally.

04 The design

Keep the WFS path

The Data Store becomes a fast path, not a replacement. The WFS path needs no credentials, already works, and is far cheaper for deep history — archive granules are 20 to 40 times larger than NRT ones, so backfilling a year through the Data Store would move gigabytes to recover six detections. Backfill stays on the WFS. The fast path covers roughly the last 24 hours and nothing more.

Credentials, following the existing pattern

Resolution order mirrors config.firms_key(): the environment (EUMETSAT_CONSUMER_KEY / EUMETSAT_CONSUMER_SECRET), then the macOS Keychain via config.keychain_secret() under service firewatch-eumetsat, and nothing in config.json. The pair is exchanged for a bearer token at https://api.eumetsat.int/token. Both values must be added to config.RedactingFormatter before the first request is ever made, not after.

The dependency, made optional

The fire pixels live in FRP_in.nc, a netCDF-4 file, which needs netCDF4 or h5netcdf plus numpy. FireWatch runs on four dependencies and the GitHub workflow installs two. This project already has a pattern for exactly this situation: geo.build_buffer() imports shapely and pyproj inside the function, so the running app never needs them. The fast path follows it — import inside the fetch, and on ImportError log once at info level and fall through to the WFS. An install without the libraries loses two hours of latency and nothing else.

Flow

  1. Discover

    Query the OpenSearch endpoint for granules intersecting the municipality bbox in the last 24 h. Anonymous, cheap, and it returns the download link per granule.

    GET https://api.eumetsat.int/data/search-products/1.0.0/os
    ?format=json&pi=EO:EUM:DAT:0417
    &bbox=17.9,44.05,18.55,44.55
    &dtstart=...&dtend=...

  2. Filter against what has already been processed

    Keep processed granule ids in the database. Expect about three new granules a day, so on almost every cycle this step ends the work with no download at all.

  3. Download and parse

    Fetch the ZIP with the bearer token, read FRP_in.nc in memory, keep pixels passing the existing geo clip.

  4. Emit detections with WFS-identical uids

    Build s3:{sat}:{lat:.4f}:{lon:.4f}:{ts} exactly as fetch_sentinel3 does, so a pixel arriving by both routes is stored once. This is the step most likely to go wrong; see landmine 1.

05 Phases

Ordered so that the cheapest work delivers standalone value and the expensive work can be abandoned without waste.

  1. Overpass awareness — no dependencies, no credentials

    The same EUMETView server already in use publishes copernicus:sentinel3a_orbital_tracks and sentinel3b_orbital_tracks. Reading them through the existing _wfs_features gives when Sentinel-3 last looked at Zavidovići, and when it looks next.

    This ships alone and is worth having on its own merits: it converts "Sentinel-3 has shown nothing for eight days" from ambiguous into answerable, which is the question that motivated this whole investigation. It also makes every later phase testable, because you know which overpasses should have produced data.

  2. Discovery and validation — still no credentials

    Add the OpenSearch query and the processed-granule bookkeeping. Log which granules would be downloaded and what the latency saving would have been, without downloading anything. Run it for a fortnight.

    This is the go/no-go gate. If it shows the fast path would have beaten the WFS on fewer than a handful of real detections, stop here — the remaining work is the expensive part and the evidence says it is not worth it.

  3. Authenticated fetch and parse

    Token handling, download, netCDF parse behind the optional import, uid construction. Validate by fetching one overpass through both routes and asserting the uid sets are identical — not merely overlapping.

  4. Integration and cutover

    Wire into poller.SOURCE_SPECS behind s3_fast_path, extend source_status so the two routes are distinguishable in /health, and document the credential in the Field Manual and the Linux and hosting guides. Rollback is flipping one setting.

06 Predicted landmines

In the spirit of the existing landmines list — these are the failures worth predicting before they cost a debugging session.

1 · Divergent uids double-count every fire

If the Data Store's coordinates or timestamps round differently from the WFS's, the same fire pixel is stored twice: n_det inflates, footprints grow, and grew alerts fire for a fire that did nothing. This is the FIRMS _NRT/_SP landmine repeating — the same instrument, the same overpass, processed twice, storing as two detections. It is the single highest risk here, and it fails silently in the direction of sending more SMS, not fewer. Gate the merge on a uid-equality test against a real overpass.

2 · A hard import kills the GitHub deployment

poll.yml installs requests and certifi and nothing else. A module-level import netCDF4 anywhere in the import graph takes down the production cycle, and it will look like a source outage rather than an import error. Keep the import inside the function.

3 · Bearer tokens expire mid-run

The token has a lifetime of roughly an hour, and the poller is a long-lived process. Cache it with its expiry, refresh on 401, and never assume a token obtained at startup is still valid on the next overpass — which, at 2.4 passes a day, is always many hours later.

4 · The granule size figure is unverified

Recent NRT granules report 431–1743 KB; granules 100 days and older report 11–21 MB. The units are not documented in the response and the discrepancy is unexplained. Three granules a day at 0.6 MB is nothing; at 21 MB it is a different conversation on a metered host. Measure one real download before committing to the design.

5 · A second credential that fails silently

FireWatch already treats a missing FIRMS key as a supported state rather than a failure. Do the same here: report not configured distinctly from failed, exclude it from /health rather than counting it down, and give it a ready()-style reason string like sms.ready().

6 · Do not let the fast path become the only path

It is tempting to retire the WFS once the Data Store works. Do not. The WFS is the credential-free route, the deep-archive route and the fallback when the netCDF libraries are absent. Losing it would mean an install without an EUMETSAT account has no Sentinel-3 at all, where today it simply has slower Sentinel-3.

07 The decision, and when to revisit it

The recommendation is not to build this now. The reasoning is proportion rather than difficulty.

Sentinel-3 has contributed 6 detections in six months. It is by a wide margin the least productive of the three feeds. This plan spends an OAuth credential, a numpy and netCDF dependency, a download-and-parse pipeline and a double-counting risk in order to make that feed two hours fresher, twice a day. The same engineering effort spent almost anywhere else in FireWatch would produce more.

Build it when one of these becomes true

— A fire in the 3–10 MW band is missed or acted on late, and the two hours would have mattered.
— Sentinel-3 starts contributing detections at a rate comparable to FIRMS, making it a feed worth optimising.
— Phase 2's dry run shows the fast path would have beaten the WFS on real detections often enough to justify phases 3 and 4.
— A deployment appears where FIRMS is unavailable, leaving Sentinel-3 as the only sensitive feed.

Phase 1 is the exception. Overpass awareness costs no dependency, no credential and no risk, uses code that already exists, and answers a question that has already come up in practice. It is worth doing whether or not the rest of this plan is ever executed.
