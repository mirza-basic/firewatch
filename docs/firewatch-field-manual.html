01 Before you start

FireWatch watches one municipality. It polls Meteosat, NASA FIRMS and Sentinel-3, groups the detections into tracked fires, tells you when something changes, and draws a live map. One process does all of it.

What you need

  • A Mac that stays awake. The whole thing is a menu bar app started by launchd at login. There is no server component; if the Mac sleeps, polling stops.
  • Python 3.14 from python.org — that is what FireWatch is developed and run on. The Homebrew build works too, but the launch agent pins whichever interpreter you install with, so pick one and stay on it. Older 3.x releases may well work (the sources parse cleanly back to 3.9) but are untested; rumps and pyobjc are the practical constraint.
  • A NASA FIRMS map key — free, issued instantly, no approval step. The other two feeds need no credentials at all.
  • Very little disk. Six months of a quiet municipality is a 184 KB SQLite file; a busy year is a couple of megabytes.
Cost

Nothing. FIRMS allows 5000 transactions per 10 minutes and a full four-dataset sweep costs 8. At the default cadence FireWatch uses well under 1% of that; run python3 -m firewatch quota to see your live usage, which is itself a free call. Meteosat and Sentinel-3 come through EUMETSAT's open WFS gateway, and the weather lookup uses Open-Meteo's free tier.

Check this before anything else

The fast feed — the one that makes near-live alerting possible — is geostationary, so it only sees one hemisphere. Roughly 60°W to 60°E: Europe, Africa, the Middle East and eastern South America. Outside that footprint FireWatch still works, but on a three-hour delay instead of twenty-five minutes. Section 09 has the measured numbers and a one-command test.

02 Install

  1. Install the dependencies

    Four packages, installed against the interpreter you intend to run:

    python3 -m pip install rumps pyobjc requests certifi

    rumps and pyobjc build the menu bar item; requests and certifi handle HTTPS.

    Do not substitute urllib

    Several Python builds ship no CA bundle, so anything using the standard library's urlopen dies with CERTIFICATE_VERIFY_FAILED while requests works fine through certifi. That is why certifi is a hard dependency and why the launch agent pins SSL_CERT_FILE.

  2. Get a FIRMS map key

    Request one at firms.modaps.eosdis.nasa.gov/api/map_key/. It arrives by email in seconds. Put it in the environment, which overrides the committed default:

    export FIRMS_MAP_KEY=your_key_here

    No key is committed to the repository. FireWatch looks in three places, in this order: the FIRMS_MAP_KEY environment variable, the macOS Keychain (python3 -m firewatch set-firms-key), then firms_map_key in your config file. Verify which one is in use:

    python3 -m firewatch quota
FIRMS key: 48 / 5000 transactions per 10 minutes
  key ...57c5 from shared default
    Running without one is fine

    A missing key is a supported state, not a failure. VIIRS/MODIS is skipped and reported as [----] rather than [FAIL], /health excludes it instead of counting it down, and Meteosat and Sentinel-3 — which need no credentials at all — carry the cycle. You lose sensitivity to small fires, not the service.

  3. Take one poll for a test drive

    From the project directory, before installing anything into launchd:

    python3 -m firewatch poll

    This runs one full cycle in the foreground and prints a report: which feeds answered, how long each took, how many detections came back, and what fires are currently tracked. Every source should say [ok]. Zero detections is a normal, healthy result — most days nothing is burning.

  4. Install the login agent

    ./firewatch-ctl install

    This generates the launchd plist against your interpreter path and CA bundle, copies it to ~/Library/LaunchAgents/, and starts it. Look for the 🌲 or 🔥 icon in the menu bar.

  5. Allow notifications

    Alerts go through osascript, which macOS attributes to Script Editor — so that is what you allow in System Settings › Notifications. Clicking such a notification does nothing.

    Install terminal-notifier instead and notifications become clickable links straight to Google Maps at the fire's coordinates:

    brew install terminal-notifier

    FireWatch picks it up automatically. python3 -m firewatch test-notify sends a sample, and notify.backend() reports which one is live.

  6. Fill in some history

    A fresh install knows nothing about the past, so the longer map ranges are empty. One deep fetch fixes that:

    python3 -m firewatch backfill 30   # about 5 minutes

    Nothing re-fetches history on its own, so this is a deliberate, occasional command rather than something that happens in the background.

04 Configuration

Settings live in ~/.config/firewatch/config.json. Anything absent falls back to the defaults in firewatch/config.py. Restart after editing.

Overrides only

The file holds only the values that differ from the defaults. That is deliberate: writing the whole resolved configuration would freeze every default at its current value, after which changing a default in code could never reach an existing install. If you edit the file by hand, keep it to the keys you actually mean to change.

Two footguns in one setting

nearby_buffer_km needs a follow-up either way you move it. Change it and run python3 -m firewatch buffer, or the band drawn on the map is stale and gets silently omitted. And narrowing it does not retroactively drop history — the clip only runs at fetch time, so detections a wider setting already let in stay in the database and on the map until python3 -m firewatch reclip --apply removes them. That command is a dry run by default and copies the database first.

Do not tighten this one

cluster_radius_km is set by Meteosat's ~4 km pixel. Below about 3.5 a single geostationary fire splits into several separate events, and every one of them alerts.

05 Alerts

Desktop notifications

These work out of the box. The only decision is whether to install terminal-notifier for clickable alerts, covered in section 02.

SMS, through your own phone

SMS goes through httpSMS, where an Android phone you own acts as the gateway — so messages come from your own number and cost whatever your carrier charges, with no third-party sending fees.

  1. Set up the gateway

    Install the httpSMS app on an Android phone, sign in, and copy the API key it shows you. That phone's number becomes sms_from.

  2. Store the key in the Keychain

    ./firewatch-ctl set-sms-key

    The key is never written to config.json. It is read from the HTTPSMS_API_KEY environment variable, or from the macOS Keychain under the service firewatch-httpsms.

  3. Add the numbers

    ./firewatch-ctl sms-add +38761234567
./firewatch-ctl sms       # shows exactly what is missing, if anything
./firewatch-ctl test-sms

    Numbers must be E.164 — leading +, country code, no spaces. One recipient is sent individually, two or more go out as a single bulk call.

    Recipients are live, the sender is not

    The two halves are configured differently on purpose. The sender is fixed for a deployment — it is the phone tied to your httpSMS account — so it goes in the environment as HTTPSMS_FROM, next to the API key. Recipients change while the service runs, so sms-add and sms-remove write config.json and the running poller picks the new list up on its next alert — no restart. That works because the recipient list is re-read at send time rather than taken from the snapshot loaded at start-up.

Why the messages have no diacritics

One non-GSM character switches an entire SMS to UCS-2 encoding, which drops the segment size from 160 characters to 70. So alert text is transliterated to ASCII — "Zavidovici", not "Zavidovići". Same information, a third of the segments.

SMS and desktop notifications are independent channels: a fire is marked notified if either succeeded, so a failing notification never silently suppresses the text message.

06 Publishing the map

The map is a local file. expose puts it behind a public ngrok URL so you can send it to someone, or leave it on a screen somewhere.

./firewatch-ctl expose      # prints the URL
./firewatch-ctl exposed     # publish state and every tunnel
./firewatch-ctl unexpose

Only two files are ever published — the map and its data file. The log, database and snapshot stay private, in a different directory entirely.

Free-tier realities
  • The URL is random and changes every time the ngrok agent restarts. A restart silently drops every tunnel it was carrying, including a URL you have already texted to people. FireWatch rebuilds the tunnel automatically each cycle while auto_expose is on, but the address will be different.
  • The agent is shared with anything else on the machine that uses ngrok, and a free account allows three endpoints per session.
  • unexpose switches publishing off, but the URL keeps resolving until the agent restarts — ngrok never actually closes a file tunnel.

07 Watching somewhere else

Nothing about the pipeline is specific to Bosnia. Pointing FireWatch at a different municipality means replacing two data files and four constants — and the whole procedure below has been run end to end against a different municipality to confirm it works.

Two files in data/ define the place. Both are build-time artifacts committed to the repository, so Nominatim and Overpass are never called while FireWatch is running:

FileHoldsComes from
zavidovici.geojsonThe municipality outline, one polygonNominatim
settlements.jsonNamed places, for "4 km SSE of Vozuća"Overpass
zavidovici-buffer.geojsonThe band drawn on the mapGenerated locally

  1. Find the boundary

    Nominatim returns the administrative relation and its polygon in one call. Search for the administrative name, not the town — searching "Kakanj" returns the town node with a Point geometry, while "Općina Kakanj" returns the boundary relation you actually want.

    curl -s -H 'User-Agent: firewatch-setup/1.0' \
  'https://nominatim.openstreetmap.org/search?q=Op%C4%87ina+Kakanj&format=json&polygon_geojson=1&limit=8' \
  | python3 -m json.tool | head -40

    Take the hit whose osm_type is relation, whose class is boundary, and whose geojson.type is Polygon or MultiPolygon. Wrap its geometry in a FeatureCollection and save it over data/<place>.geojson:

    {"type":"FeatureCollection","features":[{
  "type":"Feature",
  "properties":{"name":"Općina Kakanj","admin_level":6,
                "source":"OpenStreetMap relation 2528213","licence":"ODbL 1.0"},
  "geometry": <the geojson object from Nominatim>
}]}

  2. Fetch the settlements

    Overpass, centred on the town, with a radius comfortably wider than the municipality — places just outside it are what name a fire over the border:

    [out:json][timeout:90];
(node["place"~"^(city|town|village|hamlet)$"](around:25000,LAT,LON););
out body;

    Reshape each element to the four keys FireWatch reads — n name, k kind, lat, lon — and save as data/settlements.json:

    [{"n":"Banovići","k":"town","lat":44.40888,"lon":18.52924}, …]
    A regional mirror answers 200 and returns nothing

    Overpass mirrors are flaky — on a recent run two of three were returning 502 and 504 — so a fallback list is genuinely needed. But choose the fallbacks carefully. overpass.osm.ch is a Switzerland-only extract: it answers HTTP 200 with {"elements": []} for anywhere else, which is indistinguishable from "no settlements here". A naive retry loop lands on it, writes an empty settlements.json, and every fire is then labelled by bare coordinates. Use global mirrors — overpass-api.de and overpass.kumi.systems — retry rather than fall back to a regional one, and treat an empty result as failure.

  3. Point the code at the new place

    Four constants in firewatch/config.py:

    BOUNDARY_GEOJSON = DATA_DIR / "kakanj.geojson"
SETTLEMENTS_JSON = DATA_DIR / "settlements.json"
BUFFER_GEOJSON   = DATA_DIR / "kakanj-buffer.geojson"

# Reference point for bearings and distances: the town centre.
TOWN_LAT, TOWN_LON = 44.1754925, 18.1420167

    Use the lat and lon Nominatim returned for the relation — everything the interface says about direction and distance "of town" is measured from this point.

  4. Rebuild the map band

    python3 -m firewatch buffer

    This is the only command that needs shapely and pyproj (python3 -m pip install shapely pyproj). They are imported inside that one function, so the running app still needs only its four dependencies. Skip this step and the map simply draws no band.

  5. Fix the language and timezone

    Three things are still Bosnian. None will break anything, but all three are visible:

    • Place names in the interface — the strings "Zavidovići" and "Grad Zavidovići" in mapgen.py, menubar.py, notify.py and __main__.py.
    • The second language. The map ships a Bosnian/English toggle with full translations including Slavic plural rules. Replace the bs block in mapgen.py's I18N object, or delete it and keep English only.
    • The timezone — Europe/Sarajevo appears in enrich.py (the weather call) and mapgen.py (timestamps on the map).

  6. Start clean and verify

    The database holds detections clipped to the old boundary, which are now meaningless. Delete it and let FireWatch rebuild:

    rm ~/Library/Application\ Support/FireWatch/firewatch.db
python3 -m firewatch poll
python3 -m firewatch backfill 30

    The poll report should name settlements you recognise. If fires come back labelled with bare coordinates, settlements.json did not load — see the Overpass warning above.

Verified

Following exactly these steps against a neighbouring municipality produced a 601-vertex boundary, 506 settlements, a correctly built 2 km band, a spatial clip that accepted the town centre and rejected a point 30 km away, and a rendered map.

08 Running it on a server

The menu bar app is macOS-only. Everything else — fetching, clipping, clustering, alerting, map rendering — is portable Python, so FireWatch runs headless on a Linux host and serves the map itself.

What moves and what doesn't

PieceOn a Linux host
Polling, clustering, alerting, the map unchanged pure Python and requests
SMS unchanged the key comes from HTTPSMS_API_KEY instead of the Keychain
Desktop notifications notify-send where there is a desktop; on a headless host the alert goes to the log and SMS carries it
Data locations XDG — ~/.local/share/firewatch, ~/.cache/firewatch
The menu bar app macOS only run serve instead
./firewatch-ctl macOS only it wraps launchctl; use the systemd unit

Serving the map

On a laptop, expose goes through ngrok because there are no ports, DNS or certificates to arrange. A host with an address of its own wants the opposite — a URL that stays put — so serve runs a plain static server over the public directory:

python3 -m firewatch serve                 # 127.0.0.1:8080, and polls
python3 -m firewatch serve 0.0.0.0:8080    # answer directly
python3 -m firewatch serve --no-poll       # serve only, no polling

It polls and serves in one process deliberately: a host that serves a stale map because the poller was a second unit that quietly died is worse than either failure on its own. Only the map and its data file are reachable — the database, log and snapshot live in a different directory, directory listings return 404, and a fresh host renders an empty “no fires” map immediately instead of showing nothing until the first poll lands.

It does not terminate TLS

The default bind is loopback on purpose: putting the map on the public internet should be something you typed. For anything public, put nginx or Caddy in front — deploy/nginx.conf is a working server block. The one rule a proxy must respect is that fire-map-data.js is never cached; it is how the page learns there is a new fire.

Keeping keys out of the log

The FIRMS key travels inside the URL path, not a header. That means any connection error carries the whole query — key and all — in its exception text, and the line that reports a failed fetch wrote it straight into firewatch.log. Every log line now passes through a redacting formatter, so known credentials come out as <redacted:57c5> in messages and tracebacks alike.

Worth knowing where keys are and are not: never in the repository, config.json, the snapshot, the map, the served directory or /health. Both keys live only in the environment or the Keychain, and .gitignore now keeps __pycache__ out of git — a compiled config.pyc used to carry a copy of the key alongside the source.

Health checks

Serving and working are different questions. The static files stay perfectly readable long after polling has stopped, so a monitor that fetches / would report a healthy host indefinitely while the map quietly froze. /health answers the real question — how old is the data:

curl -fsS http://127.0.0.1:8080/health
statusHTTPMeans
ok200Snapshot is younger than health_max_age_s (15 min)
starting503No snapshot yet — the first cycle has not finished
stale503Polling has stopped, or every cycle is failing
sources_down503Fresh snapshot, but every feed failed in it

The body carries snapshot age, active fire count and per-feed status, and nothing else — no keys, no paths, no public URL. Anyone who can reach the map can reach it, so there is nothing in it worth hiding; the nginx config still keeps it to your own networks by default. /healthz is an alias, and the Dockerfile uses it as its HEALTHCHECK with a five-minute start period so a booting container is not killed while it reports starting.

Deployment files

deploy/ holds three, each commented:

  • firewatch.service — a systemd user unit. systemctl --user enable --now firewatch, plus loginctl enable-linger $USER so it survives logout.
  • Dockerfile — Python 3.14 slim, no macOS packages. Mount a volume on /var/lib/firewatch, or every restart begins with an empty database and the long ranges are blank until backfill runs again.
  • nginx.conf — TLS termination and the caching rule above.

Five environment variables cover everything a service or container needs to relocate:

The container is tested

Built and run on linux/arm64, 376 MB. All three satellite feeds polled from inside it, /health reported starting (503) during the first cycle and ok (200) once the snapshot landed, docker stop exited 0 in 0.3 s rather than being killed after the 10-second grace period, and a row written to the volume survived a restart while a volume-less container started empty. The systemd unit and the nginx block have not been exercised.

docker build -f deploy/Dockerfile -t firewatch .
docker run -d --name firewatch -p 8080:8080 \
  -v firewatch-data:/var/lib/firewatch \
  -e FIRMS_MAP_KEY=your_key_here \
  firewatch

Without -v the database starts empty on every restart and the long map ranges stay blank until backfill runs again — verified, not assumed.

10 When it goes quiet

Almost every failure mode here is silent. These are the ones that have actually cost time.

SymptomCause and fix
A code or config change has no effect The agent holds its modules in memory. ./firewatch-ctl restart
CERTIFICATE_VERIFY_FAILED Something is using urllib instead of requests, or the plist lost its SSL_CERT_FILE. Reinstall the agent
No notifications at all Allow Script Editor in System Settings › Notifications, or install terminal-notifier
Notifications appear but clicking does nothing Expected on the osascript backend. Install terminal-notifier for clickable alerts
The band vanished from the map nearby_buffer_km changed without rebuilding. python3 -m firewatch buffer
Fires shown outside the buffer you set History from a previous, wider setting. python3 -m firewatch reclip
Long ranges are empty Nothing backfills on its own. python3 -m firewatch backfill 30
Fires labelled by coordinates, no place names settlements.json is empty — almost certainly a regional Overpass mirror. Refetch from a global one
The public URL stopped resolving The shared ngrok agent restarted. ./firewatch-ctl expose for a new one
Nothing detected, ever, and you are outside Europe or Africa You are off the Meteosat disc. Section 09
40–90 day old history is missing Not a bug. FIRMS near-real-time reaches back ~40 days and the archive lags ~3 months, so that window has neither until the archive catches up

The log is the first place to look: ./firewatch-ctl logs. Every source failure is isolated and logged with the reason, and one failing feed never blocks the others.

The database is a single SQLite file with four tables and no external state, so backing it up is a copy. reclip --apply makes its own timestamped copy before deleting anything, since retention is finite and the feeds will not serve old history again.

To remove everything, delete the three directories above as well.
