Method

Fire danger forecast

The three fire feeds report detections — something is already hot. This is a different question: how conducive is today's weather to a fire starting at all, independent of whether one has. FireWatch answers it by computing the Canadian Forest Fire Weather Index (FWI) System itself, once or twice a day, at a single point.

01 Why self-computed

The obvious move was to use EFFIS/GWIS, the free European fire-danger service that already runs this exact algorithm. Measuring it directly is why this page exists instead.

EFFIS's own WMS (maps.effis.emergency.copernicus.eu/effis, layer mf010.fwi) is real, free and keyless — but at ~10 km resolution it renders this entire municipality as three or four flat-coloured blocks, confirmed by rendering it directly. And querying it for “today” returned an empty 200 response on two separate days while yesterday and the days on either side had real data — a publication gap around the current date, not a quiet sky.

Measured, not assumed

Both findings came from actually calling the service (GetCapabilities, GetMap, GetFeatureInfo) and rendering the response, in the same spirit as this project's other landmines: EFFIS's own capabilities document is advertising, and the pixels are what settle it.

Computing the same standard algorithm ourselves removes both problems: the number is anchored to one exact point rather than a coarse grid cell, and it comes from a weather feed with no such gap. What it does not do is add spatial resolution — the underlying weather model is the same order of magnitude, ~7–9 km, as EFFIS's own inputs. See §08 for why that keeps this off the map as a layer.

02 The Canadian FWI System

Six numbers, each built on the last, from four daily-noon weather readings. Developed for Canadian forests (Van Wagner 1987) and adopted by EFFIS itself as the harmonised standard for Europe, since Canada's temperate latitudes are close enough to the Mediterranean and Central Europe for the same day-length tables to hold.

Code / indexWhat it tracksMemory
FFMC
Fine Fuel Moisture Code		 Moisture in surface litter — twigs, needles, dry grass. Reacts fastest. ~1 day
DMC
Duff Moisture Code		 Moisture a few cm down, in the loosely compacted organic layer. ~2 weeks
DC
Drought Code		 Moisture in deep, compact organic soil layers — cumulative drought. ~2 months
ISI
Initial Spread Index		 Expected rate of fire spread, from FFMC and wind speed. —
BUI
Buildup Index		 Total fuel available to burn, from DMC and DC. —
FWI
Fire Weather Index		 Overall danger, from ISI and BUI — the number this page is about. —

FFMC, DMC and DC are recursive: each day's value is computed from that same code's value the day before, plus that day's noon weather. That is the whole reason this cannot be a stateless, one-shot calculation — see §06.

How each is actually calculated

The real formulas branch on rain, sign and magnitude in ways the summary table above skips. What follows is the shape of each one; firedanger.py is the exact, line-for-line source of truth, not this page.

FFMC — fine fuel moisture code m₀ = 147.2 × (101−FFMCyda) / (59.5+FFMCyda)  # yesterday's code, as a moisture % if rain > 0.5mm: m₀ absorbs it (canopy loss, then a wetting curve) m dries toward Ed or wets toward Ew — both functions of RH and temp — at a   rate set by wind speed and temperature FFMC = 59.5 × (250−m) / (147.2+m)  # clamped to [0, 101]
DMC — duff moisture code if rain > 1.5mm: yesterday's DMC is reduced by a moisture-uptake curve first K = 1.894 × (T+1.1) × (100−RH) × Le × 10⁻⁴  # Le = day-length factor, by month + latitude band DMC = (rain-adjusted DMC) + K
DC — drought code if rain > 2.8mm: yesterday's DC is reduced, more so the higher DC already is PE = (0.36 × (T+2.8) + Lf) / 2  # Lf = day-length factor for DC, same idea as Le DC = (rain-adjusted DC) + PE
ISI — initial spread index ISI = 0.208 × exp(0.05039 × WS) × f(FFMC)  # wind term × fine-fuel term
BUI — buildup index BUI ≈ 0.8 × DC × DMC / (DMC + 0.4×DC)  # corrected downward when this would exceed DMC
FWI — fire weather index B = 0.1 × ISI × f(BUI)  # f(BUI) has its own branch above/below BUI=80 FWI = B, if B ≤ 1; otherwise exp(2.72 × (0.434 × ln B)0.647)

Two numbers only mean anything with a month and a latitude attached: Le and Lf are read from fixed tables (Jan–Dec, banded by latitude) that encode how much daylight a fuel layer gets to dry in. Zavidovići's forecast point (44.39°N) falls in the same “temperate” band the tables call ≥30°N for DMC and >20°N for DC — the same band most of Canada and all of Mediterranean/Central Europe fall in, which is why EFFIS applies the identical tables across Europe without modification. firedanger.py keeps every latitude band, not just this one, so the same code works unmodified if a fork's boundary file names a point at a very different latitude.

03 Data source and point

Weather comes from Open-Meteo (api.open-meteo.com/v1/forecast), free and keyless, already used elsewhere in this project for per-event spread-risk weather. One call per computation returns hourly temperature, relative humidity, 10 m wind speed and precipitation, from which the noon reading and the 24 hour rainfall ending at noon are extracted for each local date (Europe/Sarajevo).

The point queried is geo.forecast_point() — the vertex-mean of the municipality boundary outline, not the town's own coordinates (TOWN_LAT/TOWN_LON). The town is not necessarily the geometric middle of the municipality around it, and this number is meant to characterise the whole area, the way the coarse EFFIS grid cell would. Because it is derived from whatever boundary file is configured, a fork that points that file at a different place's outline moves this point with it automatically.

04 Validation

The six formulas are a line-for-line port of Natural Resources Canada's own reference implementation, not a reconstruction from memory.

Every constant in firedanger.py was transcribed directly from github.com/cffdrs/cffdrs_py (and its R sibling cffdrs_r) — the Canadian Forest Service's own published source. tests_fwi.py then replays that same package's own published 48-day validation dataset (Van Wagner & Pickett 1985) through this port and checks every day's six outputs against the published numbers.

Result

288 of 288 daily-output checks (48 days × FFMC/DMC/DC/ISI/BUI/FWI) matched the official published values within 0.15 — comfortably inside that source's own rounding precision. A transcription mistake in a constant would fail here rather than silently mis-rating a real fire day.

As a second, independent check, this module's own output for Zavidovići on 2026-09-09 classified as Extreme — matching the dominant colour actually rendered by EFFIS's own WMS for that date over this municipality, seen by calling GetMap directly.

05 Update cadence

At most twice a day, never per poll cycle — and never less than once a day either.

FFMC/DMC/DC are a daily-timestep bookkeeping system, so recomputing every four minutes would repeat the same day's arithmetic roughly 140 times for nothing. firedanger.update() is gated on today's date plus whether local noon has passed, the same shape as imagery.refresh()'s scene-date gate for Sentinel-2: cheap to check every cycle, rare to actually do work.

First cycle after local midnight

Today's entry is built from forecast noon values, since the real noon observation has not happened yet.

First cycle after local noon

Today's entry is rebuilt from the now-actual noon observation, firming up the earlier forecast-based number.

Every other cycle

The cached result is returned with no network call at all.

Without the second gate, a fetch-once-a-day design would show a stale, forecast-only number all afternoon, even once the real weather at noon was known.

What update() actually does, in order

Called once every poll cycle (poller.py), like imagery.refresh() — almost always a fast no-op.

  1. Check the feature is on. If fire_danger_enabled is false, return None immediately — no read, no fetch, nothing shown.
  2. Resolve the point and the local clock. geo.forecast_point() gives (lat, lon); the current moment in Europe/Sarajevo gives today's date and whether the hour is ≥ 12.
  3. Read what's already known. Two small JSON blobs come out of the meta table: the gate (the date last computed, and whether noon had passed at that time) and the cached payload (the last result actually shown).
  4. Decide whether there is anything to do. Unless called with force=True (only the CLI's --force uses this), if the gate's date is today and either noon was already accounted for or it still hasn't passed — return the cached payload as-is. This is the fast path almost every cycle takes.
  5. Fetch. One Open-Meteo call for noon temp/RH/wind and 24h-to-noon rain, asking for up to SPINUP_DAYS back and fire_danger_forecast_days forward (§06 covers what actually comes back). A network failure here logs a warning and returns the cached payload — a hiccup never blanks the display.
  6. Sanity-check the window. If today's own date is not among the dates the fetch returned — which should not normally happen — log a warning and return the cached payload rather than compute on a window that does not cover “today” at all.
  7. Replay from the standard startup values (FFMC=85, DMC=6, DC=15), stepping through every returned date in order. Each day's step() call feeds that day's noon weather in and produces that day's FFMC/DMC/DC/ISI/BUI/FWI plus a danger class and colour (§07), becoming next day's input in turn.
  8. Split the replayed trend into the one entry whose date is today, and every entry after it (the forecast).
  9. Assemble and persist. Point, today's entry, the forecast list and a timestamp become the payload. The gate is written as {date: today, noon_passed} and the payload is written alongside it, both back into meta — then the payload is returned.

06 The daily replay

Rather than persisting yesterday's codes and bridging forward day by day, every run replays the entire available window from the standard startup values (FFMC=85, DMC=6, DC=15).

Bridging forward would need a separate cold-start path and a separate “gap too large to bridge” path for whenever the poller was not running. Instead, one Open-Meteo call asks for past_days=93 — one more than the API's own documented 92-day cap, so the earliest usable date still has a full 24h of hours behind it for the rain sum — and the whole window is stepped through the formulas from scratch, every time.

Measured 2026-09-10 — the documented cap is not a guarantee

The response's hourly series did span the full 93 days asked for, but the earliest ~28 of them came back with temperature, humidity and wind all null. Real data reached back only 65 days, not 92. _fetch_daily() already drops any date with a null reading — a guard originally written for a same-day hour Open-Meteo has not filled in yet, which turned out to catch this too — so a shorter real window degrades gracefully rather than computing on missing data. 65 days is still within the few-months window the fire-science literature treats as enough for the Drought Code's memory of a wrong starting value to be washed out by real rain events, but nothing in this design guarantees a particular depth on any given day.

The upside of this design: a day the poller was not running for needs no special case, because there is no stored state for it to have gone stale. Everything downstream is real weather, replayed, not a persisted guess.

08 On the map

Deliberately not a map layer, and not a marker on the map canvas.

Danger-class colours sit in the same orange-red family as the fire severity colours already used for real detections (low/moderate/high/severe). A coloured dot for “today's weather danger” drawn in that same palette would read as another fire, not a background index — and this number covers one point, not an area, so drawing it as a spatial layer would imply a coverage it does not have.

Instead it is a small panel beside the map's legend: a one-line badge (“Fire danger today: High”) that expands, on click, to the short forecast, the underlying FFMC/DMC/DC, and when it was last computed. It is collapsed by default at every screen size — both this panel and the legend used to stay permanently expanded on a desktop-sized screen, which took up too much of the map's corner, so both now share one collapse-by-default rule regardless of viewport width, rather than treating desktop and phone as two different interaction patterns.
