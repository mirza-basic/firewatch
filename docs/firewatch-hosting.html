This guide assumes FireWatch already runs on the host. Get there with FireWatch on Linux first — dependencies, keys, systemd. Command and setting reference is in the Field Manual.

01 What hosting means here

Two constraints shape every decision below, and they rule out most free application platforms.

  1. It must never sleep. FireWatch polls every four minutes. A platform that spins down on inactivity does not host a monitor, it hosts a website that occasionally monitors.
  2. It needs a persistent disk. The SQLite history is the long-range view. An ephemeral filesystem means every restart returns the year view to blank until backfill runs again.

Resource use is trivial — a 376 MB image, a couple of megabytes of database a year, and a process that is idle between polls. What you are shopping for is always-on with a volume, not capacity.

02 Serving the map

The public directory holds the map and its data file, and nothing else. serve hands those out over HTTP, and polls while it does:

python3 -m firewatch serve                 # 127.0.0.1:8080, and polls
python3 -m firewatch serve 0.0.0.0:8080    # answer directly
python3 -m firewatch serve --no-poll       # serve only

It polls and serves in one process deliberately: a host that serves a stale map because the poller was a second unit that quietly died is worse than either failure on its own. One process, one systemd unit, one thing to watch.

What is reachable

Only the map and its data file. The database, log and snapshot live in a different directory, directory listings return 404, and a fresh host renders an empty “no fires” map immediately rather than showing nothing until the first poll lands. Verified: /firewatch.db, /../firewatch.db, /..%2ffirewatch.db and /../../../../etc/passwd all answer 404.

The default bind is loopback, on purpose

Putting the map on the public internet should be something you typed. serve also does not terminate TLS — use 0.0.0.0 only if this host is meant to answer directly, and put a proxy in front otherwise.

03 TLS and a real domain

deploy/nginx.conf is a working server block: it proxies loopback, terminates TLS, and keeps /health to your own networks. Caddy does the same with less configuration and gets certificates automatically.

One rule a proxy must respect

fire-map-data.js must never be cached. It is how the page learns there is a new fire — the map refreshes in place every 60 seconds by re-fetching that one file. FireWatch sends Cache-Control: no-store for it; a proxy that overrides caching headers will freeze the map while appearing to work perfectly.

location = /fire-map-data.js {
    proxy_pass http://127.0.0.1:8080;
    add_header Cache-Control "no-store" always;
}

Everything else on the page caches happily — nothing is user-specific.

04 Health checks

Serving and working are different questions. The static files stay perfectly readable long after polling has stopped, so a monitor that fetches / would report a healthy host indefinitely while the map quietly froze.

curl -fsS http://127.0.0.1:8080/health
statusHTTPMeans
ok200 Snapshot younger than health_max_age_s (15 min)
starting503 No snapshot yet — the first cycle has not finished
stale503 Polling has stopped, or every cycle is failing
sources_down503 Fresh snapshot, but every configured feed failed in it

The body carries snapshot age, active fire count and per-feed status, and nothing else — no keys, no paths, no public URL. Anyone who can reach the map can reach it. A feed with no key is excluded rather than counted down, so an install deliberately running without FIRMS does not report 503 for ever; it appears under unconfigured instead.

/healthz is an alias.

05 Docker

docker build -f deploy/Dockerfile -t firewatch .
docker run -d --name firewatch -p 8080:8080 \
  -v firewatch-data:/var/lib/firewatch \
  -e FIRMS_MAP_KEY=your_key_here \
  -e HTTPSMS_API_KEY=your_sms_key \
  -e HTTPSMS_FROM=+38761234567 \
  firewatch
This image is tested

Built and run on linux/arm64, 376 MB. All three satellite feeds polled from inside it; /health reported starting (503) during the first cycle then ok (200) once the snapshot landed; the Docker HEALTHCHECK went healthy with a zero failing streak; docker stop exited 0 in 0.3 s rather than being SIGKILLed after the ten-second grace period; and a row written to the volume survived a restart while a volume-less container started empty.

Without -v you lose history on every restart

Verified, not assumed: a container with no volume starts with an empty database, so the long map ranges are blank until backfill runs again. Mount /var/lib/firewatch.

The image carries only what a server needs: no desktop packages, and no menu bar app. Everything else — polling, clustering, alerting, map rendering, the SMS channel — is present and works.

The HEALTHCHECK has a five-minute start-period so a booting container is not killed while it legitimately reports starting.

06 Keys and recipients

No credential is committed to the repository. On a host everything secret comes from the environment; a container or systemd unit needs no file for it.

VariableSets
FIRMS_MAP_KEYThe FIRMS key. Free, instant, per-key rate limit
HTTPSMS_API_KEYThe SMS gateway key
HTTPSMS_FROMThe gateway phone number alerts are sent from
FIREWATCH_DATA_DIRDatabase, log, snapshot, rendered map
FIREWATCH_PUBLIC_DIRThe only directory ever served
FIREWATCH_CONFIG_DIRWhere config.json is looked for
Recipients are live; the sender is not

The sender is fixed for a deployment, so it belongs in the environment. Recipients change while the service runs, so they live in config.json and sms-add applies to the running service — no restart:

docker exec firewatch python3 -m firewatch sms-add +38761234567

The list is re-read at send time rather than taken from the snapshot loaded at start-up, and the config file is written atomically because two processes now touch it.

Keys in the URL path

The FIRMS key travels inside the request path, not a header, so any connection error carries the whole query into its exception text. Every log line passes through a redacting formatter and known credentials appear as <redacted:57c5> — but if you paste logs from an older build anywhere public, check them first.

Google Cloud e2-micro — the recommendation

A real always-on VM with 30 GB of persistent disk and no expiry. The systemd unit drops straight onto it. Two things to know:

  • Free only in us-west1, us-central1, us-east1. A European region bills normally. For a static map that is about 120 ms of extra latency — irrelevant.
  • The free tier includes 1 GB/month egress. The map is ~131 KB plus a 27 KB refresh every 60 s, so roughly 580 viewer-hours per GB — ample normally, tight during an actual fire when people leave the page open. Put Cloudflare's free proxy in front and cached bandwidth stops counting, which also gives you TLS without certbot.

Oracle Always Free — and a trap specific to this app

Generous, and the ARM allowance (halved to 2 OCPU / 12 GB in June 2026) is far more than FireWatch needs. But Oracle reclaims instances averaging under about 20% CPU over seven days, and FireWatch is three HTTP calls every few minutes on an otherwise sleeping box. It is close to the definition of idle. Oracle warns before reclaiming, but you would be running something that structurally looks abandoned.

The no-VM option, and what it costs

GitHub Actions cron plus GitHub Pages needs no server at all. But Actions cron has a five-minute floor and is routinely delayed 10–30 minutes under load, and there is no disk. That drags Meteosat's ~25-minute latency out to something worse than FIRMS — discarding the one property that makes this near-live rather than a daily digest. Only worth it if “a few times a day” is genuinely enough.

Honest counterpoint

A small VPS is around €4/month with none of these caveats — no region restriction, no egress ceiling, no reclamation policy, and physically near your users. For something that sends SMS alerts about fires, that may be the better trade than engineering around a free tier.

08 Backups

The database is a single SQLite file with four tables and no external state, so backing it up is a copy. Everything else regenerates: the map, the snapshot and the public directory are rewritten from the database every cycle.

docker cp firewatch:/var/lib/firewatch/firewatch.db ./firewatch-$(date +%F).db
# or, on a plain host
cp ~/.local/share/firewatch/firewatch.db ~/backups/

What a lost database actually costs you: the long view ranges, until backfill runs again — and it can only reach as far back as the feeds still serve, which is roughly 40 days for the fast ones. Between 40 and 90 days ago FIRMS has nothing to give at all, so that window is gone for good.

reclip --apply makes its own timestamped copy before deleting anything, for the same reason.
