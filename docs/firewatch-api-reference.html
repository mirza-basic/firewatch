Every request FireWatch makes

The exact endpoints, parameters, response shapes and failure modes behind the fire data — with real captured traffic, not paraphrase.

Overview

Shared HTTP client

Every call goes through one helper so the CA bundle, User-Agent and timeout are identical everywhere.

# firewatch/sources.py
def _session() -> requests.Session:
    s = requests.Session()
    s.headers.update({"User-Agent": CFG["user_agent"]})
    return s
Why requests, not urllib

This machine's python.org framework build ships no CA bundle. Every urllib HTTPS call fails with CERTIFICATE_VERIFY_FAILED, while requests succeeds because it uses certifi. The whole codebase therefore uses requests, and the launchd agent additionally exports SSL_CERT_FILE and REQUESTS_CA_BUNDLE so anything reaching for the stdlib also works.

Timeout is http_timeout (90 s), deliberately generous because the EUMETView gateway routinely takes 15–25 s for a legitimate query.

Two parsing details that bite. acq_time is an unpadded UTC HHMM integer — 22 means 00:22, not 22:00 — so it must be zero-filled to four digits before parsing:

hhmm = (time_s or "0").strip().zfill(4)
datetime.strptime(f"{date_s} {hhmm}", "%Y-%m-%d %H%M").replace(tzinfo=timezone.utc)

And confidence changes type by sensor: VIIRS reports l/n/h, MODIS reports 0–100. We map the letters to 25/60/90 so one numeric column holds both.

EUMETView WFS Meteosat Sentinel-3

Both Meteosat and Sentinel-3 come from one OGC Web Feature Service at view.eumetsat.int/geoserver/wfs. No key, no registration, GeoJSON out.

The request we build

GET https://view.eumetsat.int/geoserver/wfs
  ?service=WFS
  &version=2.0.0
  &request=GetFeature
  &typeNames=mtg_fd:frp
  &outputFormat=application/json
  &count=3000
  &CQL_FILTER=time AFTER 2026-08-20T00:00:00Z
              AND Lat BETWEEN 44.2017 AND 44.5705
              AND Lon BETWEEN 17.9845 AND 18.5684
The single most important gotcha

BBOX(geom, …) — the obvious, spec-correct way to filter spatially — returns zero features on these layers, with HTTP 200. No error, no warning, just an empty FeatureCollection that is indistinguishable from "no fires anywhere". Spatial filtering must use the Lat and Lon attributes instead.

Captured side by side just now — identical time filter, identical area, only the spatial predicate differs:

works Lat/Lon attribute filter
CQL_FILTER=time AFTER 2026-08-20T00:00:00Z
           AND Lat BETWEEN 44.2017 AND 44.5705
           AND Lon BETWEEN 17.9845 AND 18.5684

→ HTTP 200 · 7301 bytes · "numberMatched": 18
silent BBOX geometry filter
CQL_FILTER=time AFTER 2026-08-20T00:00:00Z
           AND BBOX(geom,17.9845,44.2017,18.5684,44.5705)

→ HTTP 200 · {"features":[],"totalFeatures":0,"numberMatched":0}

Layer: mtg_fd:frp Meteosat MTG

Full-disk Fire Radiative Power from the MTG FCI instrument. Time dimension PT10M — a new slice every 10 minutes — with an archive of roughly four weeks.

200 one feature, verbatim
{"type": "Feature",
 "id": "MTG_FD_L2P_FRP_2608201050_lod0.8172",
 "geometry": {"type": "Point", "coordinates": [18.2826, 44.3069]},
 "geometry_name": "geom",
 "properties": {"Lat": 44.3069, "Lon": 18.2826,
                "FRP": 8.12, "FRPerr": 3.57, "Confidence": 68,
                "BT_mir_k": 311.2, "BT_tir_k": 301.62,
                "SZA": 31.86, "VZA": 54.24,
                "Datetime": "2026-08-20 10:58:37",
                "time": "2026-08-20T10:50:00Z"}}

Note the two timestamps and what they mean for latency measurement. time is the 10-minute slice boundary — when the instrument looked. Datetime is when the product was processed. In this feature the gap is 8 minutes 37 seconds; the remaining delay before it becomes queryable is distribution, which is what puts real end-to-end latency near 25 minutes. The id encodes the slice as DDMMYY + HHMM.

Layers: copernicus:sentinel3a_slstr_level2_frp and …3b… Sentinel-3

Same service, same query shape, queried as two separate layers and unioned. The schema differs from MTG in three fields — UsedChannel, AcrossSize/AlongSize, and Satellite — and the archive goes back over a year, which is what keeps the far edge of the 30-day view populated once MTG's four weeks run out.

Discovering the schema yourself

Two metadata calls answer "what fields exist" and "what time range is available" without guessing:

# field names and types
?service=WFS&version=2.0.0&request=DescribeFeatureType&typeNames=mtg_fd:frp

# time dimension + extent (WMS capabilities carries it, WFS does not)
?service=WMS&version=1.3.0&request=GetCapabilities
→ <Dimension name="time">2026-07-23T00:00:00Z/2026-08-21T06:10:00Z/PT10M

Open-Meteo no key

Meteorological convention

wind_direction_10m is the direction the wind blows from. A fire spreads the opposite way, so the UI shows both: from = compass(deg) and towards = compass((deg + 180) % 360). Getting this backwards would point responders at the wrong side of the fire.

Note also that the response echoes snapped coordinates — we asked for 44.3110, 18.2895 and got back 44.3056, 18.2829, the nearest grid cell, plus its elevation (934 m). Worth knowing when a value looks slightly off for the exact point.

Nominatim's usage policy requires a genuine identifying User-Agent and at most 1 request/second. We satisfy both trivially by calling it twice, ever.

Overpass failure modes

Bounding box order is (south, west, north, east) — the opposite convention from FIRMS. Overload returns HTTP 200 with an HTML error page (Dispatcher_Client::request_read_and_idx::timeout), so a JSON parse failure is the real signal. Mirrors are not equivalent either: overpass.osm.ch serves Switzerland only and answered this query with zero elements rather than an error. The fetch loop retries across overpass-api.de, kumi.systems and private.coffee with backoff, and treats an empty result as a failure worth retrying.

Map tiles browser only

The generated map loads Leaflet 1.9.4 from unpkg and raster tiles from OpenStreetMap, Esri World Imagery and OpenTopoMap. These are requested by your browser when you open the map, never by the poller.

Error handling

Three providers, three completely different ways of saying "no".

Measured failure behaviour per API
APIOn errorOn success-but-emptyHow we detect trouble
FIRMS 400 + English prose
not JSON		 200 + CSV header only Status code, plus "does line 1 look like a header"
WFS XML ows:ExceptionReport
or 502/503		 200 + empty features[] r.json() raising ValueError, and status
Overpass 200 + HTML page 200 + empty elements[] JSON parse failure; empty is also treated as failure

FIRMS errors observed directly, all with HTTP 400:

days=7          → Invalid day range. Expects [1..5].
bad dataset     → Invalid source.
bad key         → Invalid MAP_KEY.
3-value bbox    → Invalid area. Expects: [west,south,east,north].
reversed bbox   → Invalid area coordinate. West greater than East.
bad date        → Invalid year value. Expects [2000 .. 2026].

The guard that covers all of it, deliberately checking both the status and the shape of the body, because prose and CSV both arrive as text/plain:

body = r.text.strip()
if r.status_code != 200 or not body or "," not in body.split("\n")[0]:
    log.warning("firms %s: unexpected response %r", ds, body[:120])
    continue
Isolation guarantee

Each source is fetched inside its own try, and a failure records {"ok": false, "detail": …} in the snapshot rather than aborting the cycle. A real Sentinel-3 HTTP 503 during development proved it: the other two feeds completed, the map showed s3 fail, and the previously stored S3 detections still contributed to the fire because history lives in SQLite rather than in the response.

Chunking & retries

WFS query cost grows sharply — and non-linearly — with the length of the time filter. Measured against mtg_fd:frp:

Measured WFS response time by time-filter width
since_hoursDetectionsWall timeVerdict
400.5 sfine
852.3 sfine
24184.6 spoll window
721821.5 sslow, no extra data
720—> 120 snever returns

So two rules fall out. Poll windows stay at 24 h — history is in SQLite, each cycle only needs enough overlap to catch late-published slices. And backfill is chunked into 48-hour slices bounded on both ends, which is measurably faster than one wide query and cannot time out:

WFS_CHUNK_HOURS = 48.0

cql = f"time AFTER {iso(start)} AND Lat BETWEEN … AND Lon BETWEEN …"
if until is not None:
    cql += f" AND time BEFORE {iso(until)}"   # bound the far end too

A failed chunk is logged and skipped, so one bad window costs a slice of history rather than the whole 30-day backfill. FIRMS gets the same treatment for a different reason — the hard 5-day cap — by stitching six consecutive windows:

remaining = days_back
start = utcnow() - timedelta(days=remaining - 1)
while remaining > 0:
    chunk = min(5, remaining)
    out.extend(fetch_firms(days=chunk, start_date=start.strftime("%Y-%m-%d")))
    start += timedelta(days=chunk); remaining -= chunk

Transient gateway failures on the WFS get three attempts with escalating backoff (2 s, then 5 s), which turns the routine 502/503 into a small delay rather than a lost cycle.

Quota accounting

Only FIRMS is metered: 5000 transactions per rolling 10-minute window, with no documented daily cap. The per-endpoint cost is documented nowhere and had to be measured by reading current_transactions before and after each call.

Measured transaction cost
EndpointCostNote
api/area/csv/…2 Flat — independent of how many rows return, or whether zero do
api/data_availability/…/ALL5 The old shell script called this every run; we no longer do
api/data_availability/…/<one>1
mapserver/mapkey_status0 Free — safe to poll

Our steady state: 4 datasets × 2 = 8 transactions per FIRMS sweep, once per 20 minutes, so 24/hour — about 0.5% of the window. A full 30-day backfill costs 48. The other six APIs are unmetered, and the two build-time ones are already bundled.

Reproduce any of this by hand

Every call above is a plain HTTP GET you can paste into a terminal. Useful when a feed looks wrong and you want to see raw provider output rather than our parse of it.

# 1. is the key healthy, and how much budget is left? (free)
curl -s "https://firms.modaps.eosdis.nasa.gov/mapserver/mapkey_status/?MAP_KEY=$KEY"

# 2. raw FIRMS rows for the Zavidovići box, today
curl -s "https://firms.modaps.eosdis.nasa.gov/api/area/csv/$KEY/VIIRS_SNPP_NRT\
/17.9845,44.2017,18.5684,44.5705/1/$(date -u +%F)"

# 3. raw Meteosat FRP points for the last 24 h
curl -s -G "https://view.eumetsat.int/geoserver/wfs" \
  --data-urlencode "service=WFS" --data-urlencode "version=2.0.0" \
  --data-urlencode "request=GetFeature" --data-urlencode "typeNames=mtg_fd:frp" \
  --data-urlencode "outputFormat=application/json" \
  --data-urlencode "CQL_FILTER=time AFTER $(date -u -v-1d +%FT%TZ) \
AND Lat BETWEEN 44.2017 AND 44.5705 AND Lon BETWEEN 17.9845 AND 18.5684" | jq '.numberMatched'

# 4. what fields does a layer have?
curl -s "https://view.eumetsat.int/geoserver/wfs?service=WFS&version=2.0.0\
&request=DescribeFeatureType&typeNames=mtg_fd:frp"

Or go through the code, which prints the same data already parsed and clipped:

python3 -m firewatch poll        # one cycle, all sources, with per-source timing
python3 -m firewatch quota       # transaction usage
python3 -m firewatch history 40  # what actually landed in the database
