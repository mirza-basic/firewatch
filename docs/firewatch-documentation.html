FireWatch watches for active fires inside the 560 km² of Grad Zavidovići and reports them through a macOS menu bar app, desktop notifications and a live map. It replaces a shell script that polled a single NASA feed, and the whole reason it exists is timing: knowing a forest is burning eleven hours late is history, not warning.

01 The timing problem

Every satellite that detects fire does it the same way — it measures thermal infrared radiation and looks for pixels far hotter than their surroundings. What separates the sources is not how they see, but how often and how soon you find out.

Polar-orbiting satellites (VIIRS, MODIS, Sentinel-3) circle pole to pole while the Earth turns underneath, so each one passes over Bosnia only a couple of times a day. Their imagery is sharp — 375 m pixels for VIIRS — but between passes there is simply nobody looking. Geostationary satellites sit fixed above the equator and stare at the same hemisphere continuously, trading resolution for relentless repetition.

03 The data itself

A detection is one satellite pixel flagged as anomalously hot at one moment. The three feeds describe it with different fields; the most important shared one is FRP — Fire Radiative Power, in megawatts, the radiant heat output of the fire. FRP is what lets us rank severity and watch a fire strengthen or fade rather than just knowing it exists.

Confidence is not comparable across feeds

VIIRS reports confidence as letters, MODIS as a percentage, MTG and Sentinel-3 as numbers on their own scales. We normalise the VIIRS letters to l = 25, n = 60, h = 90 purely so one column can hold them all. Only MTG confidence is used as a filter (below 30 is dropped), because that is the only feed where we have enough volume for noise to matter.

04 Processing pipeline

Each cycle runs the same seven stages. Sources are polled on independent schedules, so one slow or failing feed never blocks the others.

  1. Spatial clip

    All three APIs can only be queried by rectangle, so we ask for the municipality's bounding box grown by 6 km, then test every returned point against the real outline with a ray-casting algorithm. A detection inside is inside=1; one outside but within 6 km of the border is kept and flagged nearby, because a fire two kilometres over the line still matters to you; anything further is dropped.

  2. Deduplicate into SQLite

    Every detection gets a deterministic uid — source, sensor, position to 4–5 decimals, and timestamp — and is written with INSERT OR IGNORE. Whatever the insert actually added is what is new. This is the answer to "compare with the last response": novelty is a property of the database, not of diffing two API payloads, so a detection re-reported across polls, or seen by two satellites, is only ever new once.

  3. Cluster into fire events

    Raw detections are a terrible unit for alerting. One fire produces one detection per sensor, per overpass, per hot pixel — the 20 August fire produced 45. So detections are grouped by single linkage: two belong to the same fire if they are within 3.5 km and 8 hours of each other, transitively. The radius is set by MTG's ~4 km pixels; anything tighter would split one geostationary fire into several.

    Each event then gets a stable id derived from its earliest detection, so it keeps the same identity across cycles. Footprint is the diagonal of the detection bounding box, computed in linear rather than quadratic time so a month-long fire with thousands of detections stays cheap.

  4. Enrich

    Coordinates are useless in a notification. Each active fire is resolved against 413 bundled settlements to produce a phrase like "7.0 km ESE of Kamenica", plus distance and bearing from Zavidovići town centre. Current weather comes from Open-Meteo and yields a spread-risk label from gust speed and relative humidity — elevated high extreme — because a smouldering 8 MW hotspot in 39% humidity with 32 km/h gusts is a different proposition from the same hotspot in still, damp air.

  5. Diff against the previous cycle

    The freshly built events are compared with the stored ones to produce alerts. This is covered in section 5.

  6. Notify

    Alerts become macOS notifications and, when configured, an SMS — two independent channels, so a failed notification never suppresses the text. Either way the alert is suppressed if the same event already fired for the same reason inside 25 minutes.

  7. Publish

    The cycle writes snapshot.json and regenerates the HTML map, then the menu bar rebuilds from the in-memory snapshot. Every surface reads the same published state, so they can never disagree.

05 Change detection

A fire is not an event that happens once; it starts, grows, gets confirmed by a second satellite, dies down, and sometimes comes back. The diff stage models that lifecycle so notifications carry information rather than repeating themselves.

Severity is derived from peak FRP alone: low under 10 MW, moderate 10–50, high 50–200, severe above 200 MW. For scale, the fire that prompted this system peaked at 10.5 MW — a real forest fire, at the bottom of moderate.

Observed in production

Over one unattended night the system logged exactly the cycle above: 01:53 extinguished after 4.8 h quiet, 05:54 four new detections and reignited at 1.0 MW, 06:52 extinguished again. Nobody was watching; the state machine was right.

06 Storage & time ranges

One SQLite database at ~/Library/Application Support/FireWatch/firewatch.db, four tables.

Schema
TableHoldsKey
detectionsEvery detection ever fetched, with source, position, time, FRP, confidence, day/night, inside flag and the raw provider fields as JSONuid
eventsCurrent clustered fires and their full JSON payload, rewritten each cycleid
notifiedWhat we have already told you, per event and kind — the rate limiter's memoryevent_id + kind
metaHousekeeping: last cycle, last prunek

Detections are kept 60 days and pruned at most once a day. The clustering window is 720 hours. Those two numbers are deliberately different: retention must exceed the longest view range, or the oldest data would be deleted exactly as it came into view.

Time ranges

Four rolling windows — Last 24h, 3 days, 7 days, Last month — offered identically in the map, the menu bar and the CLI. All are measured back from now rather than from midnight, so a fire never falls out of the shortest range just because the clock ticked over. An event belongs to a range if it was last active inside it, and its detection series is trimmed to the range so the sparkline and timeline stay honest about what you are looking at.

Range filtering costs no API traffic at all: each poll fetches only about 24 hours of overlap, and every range is a read over history already on disk. What the longer windows buy is pattern — the month view over Zavidovići surfaced repeated ignitions near Kamenica on 7, 15 and 17 August that no 3-day view would ever show.

07 How it reaches you

One background process owns everything: a launchd login agent runs the menu bar app, which runs the poller on a thread. There is no separate daemon to keep in sync.

Menu bar

The title encodes state so it reads without clicking — 🌲 when nothing is burning, 🔥 2!! · 48MW for two active fires with the worst at high severity and 48 MW. Each fire opens a submenu with severity, peak and current FRP, detections per satellite, distance and bearing from town, footprint, weather, spread risk, and one-click actions: Google Maps, satellite view, copy coordinates, show on map.

Notifications

Two delivery paths. osascript always works but macOS attributes the notification to Script Editor and a click does nothing. If terminal-notifier is installed, FireWatch uses it instead and the notification itself becomes a link that opens Google Maps at the fire. The app detects which is available at startup and shows it in the menu.

SMS

Alerts can also arrive as an SMS, sent through httpSMS with an Android phone acting as the gateway. Each message carries the place, severity, peak and current FRP, how many detections and from which satellites, distance and bearing from town, raw coordinates and a link to the live map — about 136 characters, one segment. Several recipients go out in a single bulk-send call.

The text is deliberately transliterated to ASCII: one non-GSM character switches an SMS to UCS-2 encoding, cutting a segment from 160 characters to 70, so “Zavidovici” costs a third of what “Zavidovići” would. SMS is an independent channel — it still goes out when the Mac is asleep and nobody sees the desktop notification.

Fire map

A self-contained HTML file, regenerated every cycle. Every 60 seconds the page pulls fresh data in place rather than reloading — the poller writes a sibling fire-map-data.js and the page injects it as a cache-busted script, because a file:// page cannot fetch a sibling JSON file but can load one as a script. Zoom, pan, selected range, timeline position and any open popup all survive the update, so it works as a live wall display that never jumps. Fire circles are sized by FRP and coloured by severity, pulsing while active; individual detections are coloured by satellite and fade with age; a scrollable timeline ruler spans the whole selected range — not merely the period containing detections, so an empty fortnight reads as empty. It carries labelled time ticks, a fixed centre playhead, and every detection as a coloured mark on the track; the step unit switches between minute, hour, day and week, and a play button at three speeds animates the fire's progression by scrolling it. The initial snapshot is still inlined for first paint, so the page renders correctly even if the data file is missing.

08 Cost & rate limits

The FIRMS key allows 5000 transactions per rolling 10-minute window — not per day, and there is no documented daily cap. Different endpoints cost different amounts, which is not documented anywhere and had to be measured:

Measured transaction cost per FIRMS endpoint
RequestCostNote
api/area/csv/…2Regardless of how many rows come back
api/data_availability/…/ALL5We no longer call this
api/data_availability/…/<one>1
mapserver/mapkey_status0Free — poll it freely

A full sweep of the four NRT datasets costs 8. At a 20-minute cadence that is 24 per hour, roughly 0.5% of budget. The old shell script cost 29 per run because it queried every dataset the availability endpoint listed, including multi-year archives and burned-area products that cannot produce a current alert. The other services are unmetered, though Nominatim and Overpass are only called once, at build time, and their results are bundled.

09 Field notes

Behaviour that is not in anyone's documentation, found by measuring. This section exists because every one of these cost real debugging time.

The WFS spatial filter silently returns nothing

BBOX(geom, …) on the EUMETView FRP layers returns zero features with HTTP 200 — no error, just an empty collection, which reads exactly like "no fires". Spatial filtering has to be done on the Lat and Lon attributes instead. Verifying against Madagascar, where fires were known to exist, is what exposed this.

WFS query cost grows sharply with the time filter

About 5 s for 24 h, 21 s for 72 h, and a 30-day query never returns at all. Long windows are split into 48-hour chunks and unioned client-side; a failed chunk is logged and skipped rather than losing the whole run. This is why backfill exists as a separate command rather than just widening the poll.

FIRMS reports errors as prose, not JSON

An invalid request returns HTTP 400 with a bare English sentence in the body — Invalid day range. Expects [1..5]., Invalid MAP_KEY., Invalid area coordinate. West greater than East. — so anything expecting a structured error has to fall back to reading the prose. The confusable case is the other direction: a valid query with no fires is HTTP 200 carrying only the CSV header, so success-with-nothing and success-with-data differ by one line. The day range cap of 5 is undocumented, which is why a month of FIRMS history is stitched from six windows.

This Python has no CA bundle

The python.org framework build ships no cert.pem, so every urllib HTTPS call fails with CERTIFICATE_VERIFY_FAILED while requests works fine via certifi. The code uses requests throughout and the launchd agent pins SSL_CERT_FILE so anything else that reaches for the stdlib also works.

Saving a whole config freezes every default

The original save() wrote the fully resolved settings dict, so the first time the menu bar persisted a preference it also froze all twenty defaults to disk — after which changing a default in code had no effect on an existing install. It cost an hour of "why is this value not updating". save() now writes only genuine overrides.

The daemon holds old code

The running agent keeps its modules in memory and keeps rewriting snapshot.json, so edits appear to do nothing and stale output looks like a logic bug. Always ./firewatch-ctl restart after changing code.

Tuning

Edit config.json and restart. The knobs that actually change behaviour: interval_mtg and interval_mtg_active for cadence; mtg_min_confidence to trade false positives against sensitivity; nearby_buffer_km for how far past the border to watch; quiet_hours for when a fire counts as out; notify_cooldown_min for alert rate limiting.

11 Limits

Read this before relying on it

These are satellite thermal anomalies, not confirmed wildfires. Industrial heat, gas flares and agricultural burning all register. This is a screening and tracking tool — verify before acting on it.

  • Not real-time. The floor is ~35 minutes behind the flame front, set by EUMETSAT's publishing latency. Nothing in this code can improve that.
  • Small fires are invisible to the fast feed. MTG's ~4 km pixels need roughly 5 MW before they register. Sub-pixel and smouldering fires are caught only by the 375 m VIIRS passes, hours later — which is exactly why all three feeds are kept rather than just the fastest.
  • Cloud blocks everything. Every one of these instruments is optical/thermal. Overcast means no detection from any of them.
  • Month view thins out at the far edge. The MTG archive holds only about 4 weeks, so the oldest part of "Last month" is covered by VIIRS, MODIS and Sentinel-3 alone — the fires are there, the 10-minute detail is not.
  • Boundary fires may flip. A detection exactly on the border can fall either side; the 6 km buffer exists so those are flagged rather than lost.
  • Local reporting is still faster. For a fire near people, a phone call beats every satellite here by hours.
